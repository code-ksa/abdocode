# النشر — تجريبيٌّ أوّلاً، ثمّ إصدارٌ يمكن الرجوعُ عنه

## 0. قبل أيّ نشر

1. البناءُ والاختبار ينجحان **محلّياً** في هذا الدور (`run npm run build`، `run npm test`)، و`release-check` لمشاريع Next.
2. الأسرارُ في الخزنة لا في المستودع: `secrets list`، و`secrets import .env` إن لم تُستورد. لا تطبع قيمة سرّ أبداً.
3. لا ترفع `.env` ولا `node_modules` ولا `.git` — `deploy` يستثنيها بنفسه.

## 1. الخادمُ التجريبيّ (لا تبنِه بيدك)

```
server sandbox <اسم> --app-port 3000
```

نداءٌ واحد: حاويةٌ بـNode 24 وSSH بالمفاتيح على 127.0.0.1 فقط، ومفتاحٌ في الخزنة، وملفُّ خادمٍ مسجَّل، وقياسُ الاتّصال. **لا** تكتب Dockerfile ولا `ssh-keygen` ولا `docker run` بيدك لهذا الغرض.

## 2. النشر

```
deploy <اسم> --env --build "npm ci && npm run build" --start "npm start" --check http://127.0.0.1:3000/api/health
```

- `--env` ينقل أسرارَ الخزنة إلى `.env` على الخادم.
- `--start`: أداةٌ تدير نفسها (`pm2 restart app || pm2 start npm --name app -- start`، `systemctl restart app`، `docker compose up -d`) تعمل كما هي؛ وغيرُها يُشغَّل في الخلفيّة بملفّ pid ويُقاس أنّه حيّ.
- `--check` يجب أن يردّ 2xx/3xx — رابطٌ على 127.0.0.1 يُفحص من داخل الخادم.
- إصدارٌ فاشل يُحذف ولا يصير `current`.

## 3. بعد النشر — اقرأ الحيّ

- `server run <اسم> -- "ss -ltnp | grep :3000; tail -n 30 <مسار النشر>/app.log 2>/dev/null"` — العمليّةُ التي تستمع هي الحقيقة (السجلُّ وملفُّ pid بجوار `current` حين يشغّله deploy في الخلفيّة).
- افتح الرابطَ في المتصفّح (`open`) وصوّر (`shot`) إن كان للمشروع واجهة.

## 4. الرجوع

`deploy <اسم> --rollback --start "<أمر التشغيل>"` يعيد `current` إلى الإصدار السابق (تبقى خمسة).

## 5. الإنتاج

- **النشرُ على خادم إنتاجٍ يحتاج موافقةَ المستخدم الصريحة في المحادثة** — ولو نجح التجريبيّ.
- خادمٌ مسجَّلٌ للنشر التلقائيّ: الدفعُ إلى فرعه نشرٌ (انظر مهارة git-push).
- قبل النشر: نسخةٌ احتياطيّة لقاعدة البيانات إن كان في الإصدار هجرة، والهجرةُ مشروطةٌ بنجاح النسخة.

## 6. بعد القياس

أزل الخادمَ التجريبيّ: `server sandbox <اسم> --remove`. وفي التسليم: الرابط، ورمزُ الحالة المقيس، واسمُ الإصدار، وأمرُ الرجوع.
